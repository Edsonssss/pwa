## Вердикт в двух абзацах

Это **качественно собранный ванильный PWA**: установка на iPhone разведена правильно (`apple-mobile-web-app-capable` + `black-translucent` + `apple-touch-icon` 180px + dual `theme-color`), safe-area учтены, maskable-иконки реально попадают в safe-zone (замерено: радиус арта 172px при лимите 205px), SW сделан по канону (precache + SWR + network-first для навигации), XSS-экранирование подтверждено тестом. Уровень выше среднего по рынку.

Но есть **три блока проблем**, из-за которых на актуальных iPhone приложение выглядит/ведёт себя хуже, чем обещает README:

1. **Стратегия статус-бара устарела на два поколения iOS.** На iOS 26 мета-тег `theme-color` больше не поддерживается, а на iOS 27 `apple-mobile-web-app-status-bar-style` (их `black-translucent`) игнорируется полностью, и установленные PWA рисуют **blur-полосу поверх верха страницы**. Их фикс-навбар не имеет собственного фона (фон лежит на дочернем `absolute`-элементе с `opacity: 0` до скролла), поэтому единственный рабочий обход на iOS 27 у них не сработает.
2. **Данные «теряются» при установке**: хранилище Home-Screen-приложения изолировано от Safari (копируются только cookie). Пользователь, который завёл задачи в Safari и затем поставил ярлык, увидит пустой демо-список — без предупреждения и без миграции/экспорта.
3. **Подтверждённые баги кода**: `save()` без `try/catch` (QuotaExceededError роняет обработчик и рассинхронизирует память и localStorage), потеря фокуса на каждый рендер, фон скроллится под открытой шторкой, на iOS невозможно снять уже поставленный срок (у нативного date-picker нет «очистить»), `.row-delete` — фокусируемая невидимая кнопка.

Ниже — всё по пунктам с готовыми правками.

## 2. Критично: статус-бар и «стеклянный» верх на iOS 26/27

Хронология поведения WebKit (проверено по заметкам Maxi Firtman, обновлено 2026-10-13, и замерам OpenPWA на iPhone 16 Pro / iOS 18.6.2):

| iOS | Поведение |
|---|---|
| ≤ 18.x | Полоса статус-бара — сплошной цвет: берётся из `theme-color` мета (если есть), иначе `theme_color` манифеста. `black-translucent` + `viewport-fit=cover` рисует страницу **под** полосой |
| **26** | `theme-color` мета **больше не поддерживается**. Установленные PWA по умолчанию рисуются fullscreen — контент под статус-баром независимо от `viewport-fit=cover` |
| **27** | `apple-mobile-web-app-status-bar-style` **депрекейтед и не работает**. Установленные PWA рисуют **blur** сверху, который спускается ниже полосы и **накрывает контент у верха страницы** |

### 2.1 Почему их текущая вёрстка не переживёт iOS 27

Единственный известный рабочий способ убрать blur на iOS 27 — `position: fixed` элемент с **фоном**:

- высота ≥ 6px;
- ширина ≥ 80% экрана;
- прижат к верху в пределах 4px.

Теперь их код (`styles.css:70–97`):

```css
.navbar     { position: fixed; top:0; left:0; right:0;  /* ✅ fixed, ✅ ширина, ✅ у верха */
              /* ❌ НЕТ background-color */ }
.navbar-bg  { position: absolute; inset:0;
              background: var(--bg-translucent);  /* ❌ полупрозрачный (rgba .82) */
              opacity: 0; }                        /* ❌ невидим до скролла */
body.scrolled .navbar-bg { opacity: 1; }
```

Сам фиксированный элемент **не имеет цвета фона** — цвет живёт на дочернем `absolute`-узле, который к тому же прозрачен до прокрутки. Итог на iOS 27 в исходном состоянии (скролл = 0, а это стартовый экран):

- blur-полоса ложится поверх large-title «Задачи», пилюли «офлайн» и поиска;
- обход «фикс-элемент с фоном» не срабатывает, потому что цвета на фикс-элементе нет.

**Правка (минимальная):** вынести цвет на сам фиксированный узел и держать его непрозрачным всегда:

```css
/* новый слой, который iOS 27 примет как «фон статус-бара» */
.statusbar-strip{
  position: fixed; top: 0; left: 0; right: 0;   /* ширина 100% ≥ 80%, у верха 0px ≤ 4px */
  height: var(--statusbar);                     /* ≥ 6px: ТОЛЬКО статус-бар, без навбар-полосы */
  background: var(--bg);                         /* сплошной, не rgba */
  z-index: 39;                                   /* под .navbar-bg, над контентом */
}
:root{ --statusbar: max(env(safe-area-inset-top), 20px); }
body { padding-top: var(--statusbar); }          /* контент начинается НИЖЕ полосы */
```

и в `index.html` первым узлом внутри `<body>`: `<div class="statusbar-strip"></div>`. Тогда blur исчезает и на светлой, и на тёмной теме. `.navbar-bg` с блюром можно оставить как декоративный слой ниже.

> **Урок с устройства (2026-10-29, скриншот iPhone):** первая версия правки задавала полосе высоту
> `inset + 44px`, и непрозрачная полоса обрезала верх large-title «Задачи». Полоса должна равняться
> ровно высоте статус-бара, а отступ контента — той же величине (`--statusbar`); итоговая формула выше.
> Проверено: blur отсутствует, глифы статус-бара тёмные и читаемые в светлой теме.

### 2.2 `black-translucent` в светлой теме (iOS ≤ 18)

`black-translucent` = прозрачная полоса + контент под ней. Цвет глифов система берёт из `color-scheme`/`theme-color`, а у вас `color-scheme: light` и мета `#f2f2f7` — то есть на iOS 15–18 глифы тёмные и всё читается. **Но** это держится исключительно на мета-теге `theme-color`, который iOS 26 уже игнорирует. Держите §2.1 как единственный источник правды и уберите двойную логику из README («особенности iOS»), чтобы не вводить будущих читателей в заблуждение.

## 3. Критично: данные и установка

### 3.1 localStorage установленного приложения ≠ localStorage Safari

WebKit (и замер OpenPWA на 18.6.2): данные Home-Screen-приложения изолированы; при создании ярлыка **копируются только cookie**, localStorage/IndexedDB — нет.

Сценарий у вас: человек открывает сайт в Safari, заводит 20 задач → жмёт «Поделиться → На экран Домой» → открывает ярлык → видит **демо-сид из трёх задач**, его данные «исчезли». Карточка-подсказка установки при этом молчит.

Что сделать (без сервера, в рамках текущей архитектуры):

1. В `app.js` при первом запуске в `standalone` показывать баннер: «Задачи, созданные в Safari, не переносятся автоматически — это ограничение iOS».
2. Добавить **Экспорт / Импорт** (кнопка в шторке или отдельный экран): `JSON.stringify({v:2, tasks})` → `navigator.share`/буфер обмена и обратный ввод. Это заодно страхует от пункта 3.2.
3. Долгосрочно — синк через сервер + Web Push, тогда изоляция перестаёт быть проблемой.

### 3.2 ITP-очистка через ~7 дней

README честно упоминает риск, но **механизма защиты нет**: ни экспорта, ни IndexedDB с персистентным запросом, ни бэкапа. Экспорт из 3.1 закрывает и это.

## 4. Баги кода (воспроизведены прогоном в jsdom)

### 4.1 `save()` без `try/catch` — падение и рассинхрон состояния

`app.js:51-53`. Тест: подменил `localStorage.setItem` на бросающий `QuotaExceededError` (реалистично: приватный режим, переполненная квота, режим «низкого объёма данных») → **uncaught error**, при этом `state.tasks` уже изменён в памяти, а `render()` не вызван (он стоит после `save()`): UI и хранилище расходятся.

```js
function save() {
  try { localStorage.setItem(STORE_KEY, JSON.stringify({ tasks: state.tasks })); }
  catch (e) {
    showToast('Не удалось сохранить: хранилище недоступно');
    return false;
  }
  return true;
}
// и в мутаторах: if (!save()) return;   // не мутируем UI, пока не сохранили
```

### 4.2 Потеря фокуса на каждый рендер

`render()` пересобирает `innerHTML` целиком → `document.activeElement` становится `<body>` (замерено). Для VoiceOver/клавиатуры каждое нажатие «галочки» выбрасывает пользователя из списка.

Минимальная правка: запоминать `data-id` строки с фокусом до рендера и возвращать фокус после; правильно — обновлять строку точечно (`row.replaceWith(newRow)`), а не весь список.

### 4.3 Фон скроллится под открытой шторкой

В CSS нет блокировки скролла: `body.sheet-open` меняет только FAB (`styles.css:290`). `overscroll-behavior-y: none` работает лишь с iOS 16, а rubber-band есть и на 15-й. Список уезжает под полупрозрачным бэкдропом.

```css
body.sheet-open{ overflow: hidden; position: fixed; inset: 0; } /* + возврат scrollY при закрытии */
```
(или `touch-action: none` на `backdrop` + сохранение/восстановление `scrollTop`).

### 4.4 Невидимая, но фокусируемая кнопка удаления

`.row-delete` — настоящая `<button>` в таб-порядке, но закрашена `.row-track` сверху. Клавиатурный пользователь табом попадает на «невидимку» и по Enter молча удаляет задачу. Либо `tabindex="-1"` до раскрытия свайпом, либо паттерн «раскрытие по клику/фокусу» с `aria-hidden`.

### 4.5 На iOS нельзя снять срок

`<input type="date">` в Safari/iOS открывает wheel-picker **только с «Готово»** — кнопки «очистить» нет. Поставленную дату невозможно убрать из UI вовсе. Добавьте рядом крестик/«Без срока», видимый при непустом `els.taskDate.value`.

### 4.6 Черновик в шторке исчезает молча

`Отмена`, тап по бэкдропу и свайп за ручку сбрасывают поля без подтверждения. «Отмена» по гайдлайнам Apple действительно сбрасывает, но тап мимо и свайп — нет. Добавьте guard «есть несохранённые правки → подтвердить».

### 4.7 `sw.js`: `respondWith(undefined)` при офлайне без кэша

- Навигация: `catch(() => caches.match('./index.html'))` — если precache упал (404 на одном файле → `addAll` откатывает всё), вернётся `undefined` → TypeError вместо офлайн-страницы.
- SWR: `.catch(() => cached)` — тот же `undefined`, если кэша нет.

Добавьте синтетический ответ:

```js
const offlineHTML = () => caches.match('./index.html')
  .then(r => r || new Response('<meta charset="utf-8"><h1>Нет сети</h1>',
        { headers: { 'Content-Type': 'text/html; charset=utf-8' }, status: 503 }));
```

### 4.8 `skipWaiting()` в `install` противоречит README

`sw.js:23` вызывает `skipWaiting()` сразу, а README обещает «обновление при следующем открытии». При живом старом клиенте новый SW забирает управление mid-session: DOM старый, ассеты новые → рассинхрон. Либо уберите `skipWaiting` и показывайте тост «Доступна новая версия — обновить», либо оставьте и поправьте README.

### 4.9 Установленное приложение может жить на старом коде днями

`reg.update()` не вызывается нигде, кроме навигации. iOS держит PWA в фоне suspend/resume без navigation-события. Стандартный паттерн:

```js
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible')
    navigator.serviceWorker.getRegistration().then(r => r?.update());
});
```

Плюс `{ updateViaCache: 'none' }` при регистрации (поддерживается с iOS 15) — чтобы HTTP-кэш хостинга не держал старый `sw.js`.

### 4.10 Производительность рендера

- `render()` вызывается на **каждый** `input` поиска без debounce — на 500+ задачах это полная пересборка DOM на каждый символ.
- `visibleTasks()`/`rowHTML()` создают `new Date()` и **новый `Intl.DateTimeFormat` на каждую строку** на каждый рендер (`dueLabel`, `dueClass`, `shiftDays`). Вынесите форматтеры и `todayStr()` в константы модуля/кэша на рендер.
- `will-change: transform` на **каждой** `.row-track` (`styles.css:202`) форсирует compositor-слой на строку: на iOS это известный источник просадок памяти и «мигающих» строк. Ставьте класс `dragging` + `will-change` только во время свайпа (он у вас уже есть).
- Дебаунс поиска ~120 мс + `requestAnimationFrame`-батчинг решают остальное.

## 6. Доступность: системные пробелы (замерено)

| Что | Факт | Норма / правка |
|---|---|---|
| Галочка задачи | `role`, `aria-pressed`/`aria-checked` отсутствуют → VoiceOver не объявляет состояние | `role="switch"` + `aria-checked` или `aria-pressed` |
| Шторка | нет `role="dialog"`, `aria-modal`, ловушки фокуса, Escape; фокус не возвращается на FAB | добавить всё перечисленное |
| Тост «Вернуть» | нет `role="status"`/`aria-live` → undo не объявляется | `role="status"` |
| Табы | `aria-controls` нет, `tabpanel` нет, стрелки не работают | либо довести tablist, либо заменить на обычные кнопки-фильтры с `aria-pressed` |
| Список | `aria-live="polite"` на всём контейнере → при вводе в поиск зачитывается **весь список** | убрать `aria-live` с `#list`, оставить отдельный счётчик-`status` |
| Фокус-кольца | `outline: none` у поиска, заголовка, заметки, даты — без замены | `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px }` |
| Контраст (замер) | placeholder `--tertiary` 1.98:1 (светлая) / 2.84:1 (тёмная на карточке) при норме 4.5; `--secondary` на фоне 2.92:1; точка приоритета `#ff9500` на белом 2.20:1 при норме 3.0 для non-text | затемнить токены: tertiary → `#8e8e93`/`#98989d`, prio-dot → `#c77700`-подобный |
| Цели касания | `.check` 24×24, `.seg` ≈ 32px по высоте, `.install-close` 26×26 — при рекомендации Apple 44×44 pt | расширить hit-area псевдоэлементом `::after { inset: -10px }` |
| Safe-area по горизонтали | `.content`, `.card`, `.search-wrap`, `.segmented` не добавляют `env(safe-area-inset-left/right)` — в landscape с «чёлкой» края уезжают под вырез (у FAB и install-card учтено — непоследовательно) | добавить инсеты |

## 7. Манифест: что iOS просто игнорирует (firt.dev, 2026-10-13)

| Поле / фича | На iOS | Последствие для вас |
|---|---|---|
| `shortcuts` | ❌ (только macOS 17.4+) | README рекламирует ярлык «Новая задача» — **на iPhone его не будет**; работает только в Chrome/Android |
| `background_color` | ❌ | цвет сплэша не управляется |
| `display_override` | ❌ | мёртвый вес, работает `display` |
| `purpose: maskable` | ❌ игнорируется | вас спасает `apple-touch-icon`; маскабельные нужны только Android |
| `beforeinstallprompt` / `appinstalled` | ❌ | ваша iOS-ветка с инструкцией «Поделиться» — единственно верная ✅ |
| SVG-иконки в манифесте | ✅ с iOS 26 | ок как fallback |
| `lang`, `dir`, `orientation` | ❌ | безвредно |
| Web Push | ✅ 16.4+, только установленные | см. Declarative Web Push 18.4+ |
| Background/Periodic Sync | ❌ | README честен ✅ |
| С iOS 26 | любой сайт по «На экран Домой» открывается как web app | ваш manifest всё равно используется, включая иконки ✅ |

Отдельно: `<link rel="mask-icon" href="icons/icon.svg">` (`index.html:21`) — Safari для закреплённых вкладок берёт **только альфа-канал**. У вас SVG = сплошной градиентный квадрат → закреплённая вкладка покажет синий квадрат вместо галочки. Нужен монохромный силуэт.

## 8. Гигиена репозитория

- README описывает `serve.js`, `tools/gen-icons.js`, `tools/test/smoke.js`, `npm start`, `npm test`, `npm run icons` — **ни одного из этих файлов в репозитории нет** (в tracked-файлах только 6 исходников + README + иконки). Обещания «20 проверок» невыполнимы: `npm test` падает сразу.

- История — один коммит «Add files via upload»: нет ни changelog, ни возможности отката.
- Схема хранилища `{ tasks: [...] }` без номера версии: миграции в будущем некуда деть. Сид из трёх демо-задач подмешивается в рабочий инструмент при первом запуске.
- Нет `<noscript>` и фолбэка без JS.

## 13. Мультипользовательский режим, синхронизация и экспорт .json (2026-10-29)

Запрос: «экспорт в JSON на сайте», «чтобы пользоваться могли несколько человек», «данные у каждого свои».
Уточнения заказчика: аккаунты с синхронизацией между устройствами (нужен бэкенд), PIN на профиль,
экспорт — прямое скачивание файла `.json`, системный share-лист сохраняется как второй вариант.

### Архитектурные решения

| Решение | Почему |
| --- | --- |
| Один процесс `server.js` отдаёт и статику, и `/api/*` | Тот же origin: нет CORS, SW и офлайн-режим не меняются, деплой — одна команда |
| Файловая БД (`data/users.json`, `tokens.json`, `tasks/<uid>.json`), запись через tmp+rename | Ноль зависимостей, атомарность, достаточный запас для семьи/небольшой команды |
| Синхронизация last-write-wins по `updatedAt` | Простая и предсказуемая модель без векторных часов; конфликт «обе правили» решается в пользу свежей |
| Удаления — надгробия (`deleted: true`, TTL 30 дней на клиенте и сервере) | Иначе удаление на одном устройстве «воскресало» бы при pull с другого |
| Локальный режим сохранён полностью | Приложение обязано работать офлайн и без аккаунта (GitHub Pages, первая установка) |
| PIN — PBKDF2-SHA256 120 000 итераций, только в `localStorage` устройства | Требование «замок на устройство», а не сквозное шифрование; честно описано в README |
| Экспорт: `a[download]` + отдельно `navigator.share({files})` | На iOS «Поделиться» не всегда даёт «Сохранить в Файлы» первым шагом, а скачивание работает предсказуемо |

### Доступность новых экранов

- Шторки аккаунта и PIN — `role="dialog" aria-modal="true"` с `aria-labelledby`, Escape закрывает их по приоритету (PIN → аккаунт → задача), не трогая чужие диалоги.
- Ошибки входа и PIN — `role="alert"`, текст появляется до фокуса на поле; `aria-haspopup="dialog"` на чипе аккаунта.
- Экран блокировки получает фокус сразу после открытия; разблокировка не оставляет фокус в скрытом элементе.
- Индикатор синхронизации (`sync-dot`) помечен `aria-hidden`, состояние продублировано текстом в шторке аккаунта и объявляется через `role="status"` у тоста.
- Контраст новых компонентов: залитая кнопка `#0066d6` + белый = **5.42:1** (светлая тема), тёмная тема `#0a84ff` + `#00182f` = **4.91:1**; текстовые кнопки на карточке используют `--accent-text` (5.42:1 / 7.07:1), «Выйти» — `--red` (6.54:1 / 6+:1). Все значения ≥ 4.5:1, AA выполнено.
- Зоны касания кнопок ≥ 46 px, чип аккаунта 34 px увеличен невидимой областью (как у остальных мелких контролов проекта).

### Безопасность

- CSP `default-src 'self'` (+ `style-src 'unsafe-inline'` для inline-стилей анимаций), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- Пути `/data/`, `node_modules`, dot-сегменты статикой не отдаются (проверено тестом `api.mjs`).
- Пароли — scrypt с индивидуальной солью; токены — 32 байта hex, TTL 30 дней, отзыв по `/api/logout`.
- Rate-limit авторизации: 30 запросов в минуту с IP.
- Service worker не кэширует `/api/*` — иначе pull возвращал бы устаревшие задачи, а 401 кэшировался бы как успех.
- Серверная санитизация входящих задач дублирует клиентскую (title ≤ 140, note ≤ 500, `due` — только ISO-дата, `prio ∈ {0,1,2}`, id ≤ 64, ≤ 5000 задач за запрос).

### Проверено тестами

- `npm run test:smoke` — **75 проверок** (jsdom): прежние 31 регресс-проверка плюс экспорт `.json` (имя файла, состав, `account`), импорт со слиянием LWW, надгробия и undo, вход в аккаунт с переносом локальных задач, Bearer-push, pull с курсором `since`, отрисовка подтянутой задачи, установка/проверка PIN, блокировка-разблокировка, выход с сохранением локальных данных.
- `npm run test:api` — **24 проверки** (`server.js` на эфемерном `DATA_DIR`): регистрация/вход/дубликаты/короткий пароль, 401 после logout, LWW-слияние, дельта по `since`, санитизация, статика и блокировка служебных путей, CSP.

### Известные ограничения (осознанно, на вырост)

- Нет смены/сброса пароля, подтверждения e-mail, удаления аккаунта и 2FA.
- Синхронизация «по требованию» (открытие приложения, правка, появление сети), не realtime; конфликты без истории версий.
- Файловая БД и один процесс: для сотен активных пользователей нужен Postgres — контракт `/api/*` при этом сохраняется.
- Общий доступ к спискам между пользователями не реализован: данные строго личные (этого и просил заказчик).


## 14. Диагностика «Сервер недоступен» на устройстве (2026-10-29)

Проверка на iOS дала общую фразу «Сервер недоступен. Проверьте сеть или где развёрнут API» при регистрации.
Причина — в клиенте: любая ошибка (нет API на статическом хостинге, сервер не запущен, офлайн,
HTML вместо JSON, неожиданный ответ) сваливалась в один `catch` с одним текстом.

Что исправлено:

1. **`GET /api/health`** — публичный эндпоинт (без токена): `{ok, name, version, time}`. По нему и человек, и клиент отличают «API развёрнут» от «тут статика».
2. **Зонд в шторке аккаунта**: строка состояния (`role="status"`) — «сервер синхронизации отвечает» / «сервер не отвечает: по адресу … нет API» / «нет подключения». Классы `.ok`/`.bad` используют `--accent-text` и `--red` (AA).
3. **Разбор ответа вместо одного `catch`**: отдельно сетевая ошибка, отдельно `!res.ok` с текстом сервера, отдельно 404 («нет API: приложение открыто без server.js»), 5xx, и «ответ без токена» (на адресе не этот сервер). Перед показом сетевой ошибки зонд выполняется заново, чтобы текст не описывал устаревшее состояние.
4. **Внешний адрес API**: блок «Сервер синхронизации» в шторке аккаунта (`localStorage['pwa-tasks:api-base']`) — для схемы «статика на GitHub Pages, `server.js` на другом хостинге». На сервере добавлен `ALLOWED_ORIGINS` (echo разрешённого origin + `Vary`, preflight `OPTIONS` → 204); без переменной CORS-заголовков нет вовсе. CSP `connect-src` расширяется списком разрешённых origin.
5. `send()` отдаёт `X-Content-Type-Options: nosniff` и для JSON-ответов API (раньше — только для статики).

Проверки: `npm run test:api` — **29** (добавлены health, preflight разрешённого/чужого origin, CORS-заголовок на GET), `npm run test:smoke` — **83** (состояние сервера, сохранение/сброс внешнего адреса API, запрос health по внешнему адресу, внятный текст при недоступном API, отсутствие «фейкового» аккаунта после ошибки).

### Дополнение: статический хостинг без API (решение заказчика — остаться на GitHub Pages)

Заказчик открывает приложение с GitHub Pages, где `/api/*` не существует, и поднимать сервер не планирует.
Поэтому «нет API» — штатный режим, а не ошибка:

- Зонд `/api/health` различает три исхода: `ok` (server.js отвечает), `missing` (404/HTML — статика), `unreachable` (сеть/сервер недоступен). Раньше все три выглядели одинаково («Сервер недоступен»).
- В состоянии `missing` кнопки «Войти»/«Создать аккаунт» **скрыты**, вместо них — текст про локальный режим и перенос через «Экспорт .json» → «Импорт»; индикатор синхронизации серый, а не красный (красный оставлен для `unreachable`).
- Зонд выполняется один раз при старте (если аккаунта нет), поэтому шторка аккаунта открывается уже с правильным состоянием, без ожидания.
- Блок «Сервер синхронизации» остаётся доступным: статика может жить на Pages, а API — на отдельном хостинге (`ALLOWED_ORIGINS`).
- Проверки: `npm run test:smoke` — **92** (добавлено окружение «статический хостинг»: 404 на `/api/*`, скрытые кнопки входа, объяснение, серый индикатор, работающий экспорт, отсутствие аккаунта), `npm run test:api` — **29**.
