# Задачи — PWA для iOS

Офлайн-PWA «список дел» в стиле нативного iOS. Чистый HTML + CSS + JS: **без сборки, без фреймворков, без зависимостей** в рантайме. Раскладывается на любой статический хостинг с HTTPS и ставится на iPhone как обычное приложение.

Приложением могут пользоваться **несколько человек**: каждый ведёт задачи локально без аккаунта, а при желании создаёт аккаунт — и тогда его задачи синхронизируются между его устройствами. Данные пользователей изолированы: у каждого своё хранилище на сервере и свой ключ в браузере. Бэкенд — один файл `server.js` на чистом Node (без npm-пакетов).

## Что умеет

- **iOS-внешность**: large title со схлопыванием в навбар, grouped-списки, segmented-контрол, bottom sheet с «ручкой», системные цвета и тёмная тема, safe-area под «чёлку» и home-индикатор.
- **Задачи**: создание/редактирование в шторке, срок (нативный date-picker + кнопка «убрать срок»), приоритет, заметка, поиск, вкладки «Все / Сегодня / Готово».
- **Жесты**: свайп строки влево — удаление (как в Mail), свайп вниз за ручку — закрыть шторку, toast с «Вернуть».
- **Офлайн**: service worker кэширует оболочку (stale-while-revalidate + network-first для навигации + офлайн-страница), задачи лежат в `localStorage`. Индикатор «офлайн» в шапке.
- **Установка**: manifest + иконки (180/192/512 + maskable), подсказка «Поделиться → На экран “Домой”» для Safari и нативный prompt в Chrome/Android. Ярлык «Новая задача» (`?new=1`) работает в Chrome/Android: iOS манифестные `shortcuts` не поддерживает.
- **Несколько пользователей**: аккаунт по e-mail и паролю, у каждого свои задачи; локальный режим без аккаунта продолжает работать (и офлайн).
- **Синхронизация между устройствами**: last-write-wins по `updatedAt`, удаления — «надгробиями», офлайн-правки уезжают при появлении сети; индикатор состояния на чипе аккаунта.
- **PIN на устройство**: локальная блокировка приложения (PBKDF2-SHA256, 120 000 итераций, соль), экран ввода PIN при запуске и кнопка «Заблокировать».
- **Данные**: «Экспорт .json» сразу скачивает файл `pwa-tasks-ГГГГ-ММ-ДД.json`, «Поделиться» отдаёт его через системный share-лист (AirDrop, Почта, «Файлы», Telegram); импорт **сливает** задачи по LWW, ничего не затирая.
- **Обновления**: новый service worker не рвёт живую сессию — появляется тост «Доступна новая версия → Обновить»; проверка обновлений также при возврате в приложение.
- **Доступность**: шторка как `dialog` с ловушкой фокуса и Escape, галочки как `switch` с `aria-checked`, вежливый анонс счётчика, видимые фокус-кольца, контраст токенов по WCAG AA, зоны касания ≥44 pt.
- Счётчик активных задач в `document.title`, стаггер-анимации, `prefers-reduced-motion`.

## Запуск локально

```bash
npm start                 # node server.js 8080 — приложение + API (аккаунты, синхронизация)
npm run serve:static      # только статика: локальный режим без аккаунтов
python3 -m http.server 8080   # либо любой другой статик-сервер
```

Service worker регистрируется **только по HTTPS или localhost** — для проверки на телефоне нужен HTTPS-хостинг или туннель.
`crypto.subtle` (нужен для PIN) тоже доступен только в secure-контексте, поэтому на `http://` без localhost кнопка PIN скрыта.

## Установка на iPhone / iPad

1. Задеплойте папку на HTTPS-хост (см. ниже).
2. Откройте ссылку в **Safari** (не во встроенном браузере Telegram/Instagram — там установка недоступна).
3. Кнопка **«Поделиться»** (квадрат со стрелкой вверх) → **«На экран “Домой”»** → «Добавить».
4. Иконка появится на рабочем столе; приложение открывается полноэкранным, без адресной строки Safari.

При первом входе приложение само покажет карточку-подсказку с этими шагами.

## Деплой

### С синхронизацией (server.js)

```bash
PORT=8080 DATA_DIR=/var/lib/pwa-tasks node server.js
```

- Node ≥ 18, зависимостей нет (`npm install` нужен только для тестов).
- `DATA_DIR` — куда писать `users.json`, `tokens.json`, `tasks/<userId>.json` (по умолчанию `./data`, каталог в `.gitignore`). Держите его на постоянном диске и в бэкапах: это и есть база.
- Порт: аргумент (`node server.js 8080`) или `PORT`.
- **Обязательно за HTTPS-реверс-прокси** (nginx/Caddy/Traefik): пароли и токены идут в заголовках. Caddy-пример: `reverse_proxy / caddy.example.com 127.0.0.1:8080`.
- Процесс-менеджер: `systemd`, `pm2 start server.js --name tasks` или контейнер.
- Сервер отдаёт статику и API **с одного origin** — поэтому CORS не нужен, а service worker и офлайн-режим работают как раньше.
- Быстрая проверка после деплоя: откройте `https://ваш-домен/api/health` — должен вернуться `{"ok":true,...}`.

**Статика на одном хостинге, сервер на другом** (например, GitHub Pages + Render/VPS):
```bash
ALLOWED_ORIGINS="https://USER.github.io" PORT=8080 node server.js
```
Тогда в приложении: чип аккаунта → «Сервер синхронизации» → вписать адрес API → «Сохранить и проверить».
`ALLOWED_ORIGINS` принимает список origin через запятую (или `*` для любого — только для отладки);
без него сервер работает строго same-origin и CORS-заголовков не отдаёт.

### Только статика (без аккаунтов)

**Netlify Drop** — самое быстрое: откройте <https://app.netlify.com/drop> и перетащите папку (или архив `pwa-tasks.zip`). Получите `https://….netlify.app`.

**GitHub Pages**
```bash
git init && git add -A && git commit -m "pwa"
git branch -M main && git remote add origin https://github.com/USER/REPO.git
git push -u origin main
# Settings → Pages → Deploy from branch → main / root
```
Все пути в проекте относительные (`./`), поэтому подпапка `/REPO/` работает без правок; SW зарегистрируется с scope подпапки. На статическом хостинге API нет: приложение остаётся полностью рабочим в локальном режиме, а попытка входа сообщит, что сервер недоступен. Для синхронизации нужен вариант с `server.js` выше.

**Vercel / Cloudflare Pages** — импорт репозитория, framework: *Other / None*, output directory: корень (`.`).

После деплоя проверьте: DevTools → Application → Manifest (ошибок нет), Service Workers (статус *activated*), Lighthouse → PWA.

> Для GitHub Pages в репозитории уже лежит `.nojekyll` (иначе Jekyll может вырезать служебные файлы). На Netlify/Cloudflare он безвреден.

## Аккаунты, синхронизация и приватность

**Кто что видит.** Задачи принадлежат аккаунту: сервер хранит их в `data/tasks/<userId>.json` и отдаёт только по токену этого пользователя. Два человека на одном сервере не видят данные друг друга; на одном устройстве у каждого аккаунта свой ключ в `localStorage` (`pwa-tasks:v2:<userId>`), у локального режима — `pwa-tasks:v1`.

**Как устроена синхронизация.**
- У каждой задачи есть `updatedAt`; конфликт решает **last-write-wins** (свежая запись побеждает).
- Удаление — не удаление строки, а флаг `deleted: true` («надгробие»): так удаление доезжает до других устройств. Надгробия старше 30 дней чистятся и на клиенте, и на сервере.
- Клиент отправляет свой набор задач и `since` (курсор последней синхронизации), сервер отвечает задачами, изменившимися после этого момента; клиент сливает их через `mergeTasks`.
- Триггеры: вход в аккаунт, любое изменение (дебаунс 1,5 с), возврат в приложение, появление сети, кнопка «Синхронизировать сейчас». Офлайн-правки никуда не теряются и уезжают позже.

**Авторизация.** `POST /api/login|register` возвращает Bearer-токен (32 байта hex, TTL 30 дней); пароль хранится как scrypt-хэш с солью. Токен лежит в `localStorage` этого устройства; «Выйти» отзывает его на сервере. Rate-limit на авторизацию: 30 попыток в минуту с IP.

**PIN.** Это локальный замок на устройство, а не шифрование данных: PIN превращается в хэш PBKDF2-SHA256 (120 000 итераций, случайная соль) и хранится в `pwa-tasks:pin:<userId>`. Восстановления нет — сброс через очистку данных сайта (сами задачи при этом остаются в аккаунте на сервере).

**API**

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/register` | создать аккаунт `{email, password≥8}` → `{token, user}` |
| POST | `/api/login` | вход → `{token, user}` |
| POST | `/api/logout` | отозвать текущий токен |
| GET | `/api/me` | проверить токен |
| GET | `/api/health` | публичная проверка доступности (клиент показывает «сервер отвечает / не отвечает») |
| GET | `/api/tasks?since=<ms>` | задачи, изменённые после `since` |
| POST | `/api/tasks` | `{since, tasks[]}` — запушить свои и получить чужие изменения |

Сервер валидирует и обрезает поля (title ≤ 140, note ≤ 500, `due` — ISO-дата, `prio ∈ {0,1,2}`, ≤ 5000 задач за запрос), отдаёт CSP `default-src 'self'`, `X-Content-Type-Options: nosniff` и закрывает `/data/`, `node_modules` и dot-пути.

**Если при входе написано, что сервер недоступен.** Приложение различает три ситуации и пишет конкретную причину под формой:

| Что написано | Что это значит |
| --- | --- |
| «сервер синхронизации отвечает» | API на месте, вход должен работать |
| «сервер не отвечает: по адресу … нет API» | Сайт открыт со статического хостинга (Pages/Netlify) или `server.js` не запущен/недоступен |
| «Нет подключения к интернету» | Офлайн: задачи сохраняются локально, вход выполните позже |

Проверка вручную: откройте `<адрес сайта>/api/health` (или адрес из блока «Сервер синхронизации») — должен вернуться JSON `{"ok":true,...}`. Если открыт старый установленный ярлык, обновите приложение: тост «Доступна новая версия → Обновить» или двойное закрытие/открытие.

**Честные ограничения.** Это файловая база и один процесс: для семьи/команды из нескольких человек — хорошо; для сотен активных пользователей стоит перейти на Postgres, сохранив тот же контракт API. Синхронизация «по требованию», а не realtime: изменения подтягиваются при открытии приложения и после правок.

## Особенности и ограничения iOS (честно)

- **Статус-бар по версиям iOS**: до 18.x цвет полосы брался из `<meta name="theme-color">`; с iOS 26 этот мета-тег игнорируется, а с iOS 27 игнорируется и `apple-mobile-web-app-status-bar-style`, и установленные PWA рисуют blur поверх верха страницы. Обход, который работает: сплошной `position: fixed` элемент с фоном у самого верха (≥6 px высотой, ≥80% ширины, ≤4 px от верха) — в проекте это `.statusbar-strip`. Мета-теги оставлены как fallback для iOS ≤ 25.
- **Хранилище изолировано от Safari**: при добавлении ярлыка копируются только cookie, `localStorage`/IndexedDB — нет. Поэтому задачи, заведённые в Safari, не появятся в установленном приложении; при первом запуске установленного PWA показывается предупреждение. Лечится двумя способами: аккаунт с синхронизацией (данные живут на сервере) или резервная копия через «Экспорт .json» → «Импорт».
- **ITP-очистка**: WebKit может очистить данные сайта, к которому не обращались ~7 дней. Для установленного PWA это маловероятно, но экспорт остаётся рекомендованной практикой.
- **Push-уведомления**: доступны с iOS 16.4+ и только для установленных на домашний экран PWA, через Web Push (VAPID) + собственный сервер отправки. С iOS 18.4 есть Declarative Web Push (`window.pushManager`) без обязательного service worker. В этой сборке пушей нет — при желании подключается отдельно.
- **Фоновая синхронизация и бейджи** на иконке в iOS для web недоступны.
- **Манифестные поля, которые iOS игнорирует**: `shortcuts` (только macOS 17.4+), `background_color`, `display_override`, `purpose: maskable` (на iOS иконку задаёт `<link rel="apple-touch-icon">`). Ярлык «Новая задача» (`?new=1`) поэтому работает в Chrome/Android.
- **Splash-экран** при запуске iOS рисует сам по снимку/иконке; отдельные `apple-touch-startup-image` не подключались сознательно (их нужно по размеру на каждую модель).
- **Обновление SW**: новый worker встаёт в очередь и не перехватывает живую сессию (`skipWaiting` только по явному действию пользователя из тоста). Дополнительно `reg.update()` вызывается при возврате в приложение, а регистрация идёт с `updateViaCache: 'none'`, чтобы HTTP-кэш хостинга не держал старый `sw.js`.
- **С iOS 26** любой сайт, добавленный на экран «Домой», открывается как web app по умолчанию; манифест и иконки при этом используются.

## Кастомизация

- **Имя/цвета установки**: `manifest.webmanifest` (`name`, `short_name`, `theme_color`, `background_color`) и `<meta name="theme-color">` в `index.html`.
- **Иконки**: отредактируйте градиент/галочку в `tools/gen-icons.js` и выполните `npm run icons`.
- **Палитра UI**: блок токенов в начале `styles.css` (`:root` и `@media (prefers-color-scheme: dark)`).
- **Хранилище**: ключи `pwa-tasks:v1` (локальный режим) и `pwa-tasks:v2:<userId>` (аккаунт) в `app.js`; при желании заменяются на IndexedDB без изменения UI.
- **Синхронизация**: дебаунс `scheduleSync()`, TTL надгробий `TOMBSTONE_TTL_MS` (`app.js`) и логика слияния на сервере (`server.js`, `mergeIncoming`).
- **Лимиты аккаунтов**: минимальная длина пароля, TTL токена и rate-limit — константы в начале `server.js`.
